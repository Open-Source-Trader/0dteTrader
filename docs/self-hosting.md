# Self-hosting the backend

Run your own private 0dteTrader backend in one click, then point the apps at it. No terminal, no config files.

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/0dtetrader-template)

## What gets created

Pressing the button deploys three services into **your own Railway account** (your project, your billing — the 0dteTrader maintainers never see or control your instance):

| Service    | What it is                                                  | Storage           |
| ---------- | ----------------------------------------------------------- | ----------------- |
| `api`      | The NestJS backend, built from this repo                    | —                 |
| `Postgres` | Your database (users, encrypted broker credentials, orders) | persistent volume |
| `Redis`    | Cache / stream infrastructure                               | persistent volume |

Typical cost is a few dollars per month on Railway's usage-based pricing (their Hobby plan includes a monthly usage credit).

## Deploy walkthrough

1. Press **Deploy on Railway** above (create a free Railway account if you don't have one).
2. Press **Deploy Now**. There is nothing to configure — no environment variables, no secrets.
3. Wait for the three services to go green (the first `api` build takes a few minutes).
4. Open the `api` service → **Settings** → **Networking** and copy the public URL Railway assigned (something like `https://api-production-xxxx.up.railway.app`).
5. Sanity check: open `<your-url>/v1/health` in a browser — you should see `{"status":"ok","db":"ok",...}`.

## Connect the apps

On the **login screen** of the desktop or iOS app, open the **Server** section, paste your URL, hit **Test connection**, then **Save**. The app remembers it across restarts; register your account and trade. (Use **Reset to default** to go back to the standard backend.)

## How secrets work

You weren't asked for any secrets because the backend provisions itself:

- **Database and Redis passwords** are generated by Railway at deploy time, unique to your instance.
- **JWT signing secrets and the credential-vault encryption key** are generated by the API on first boot and stored in _your_ Postgres (`runtime_secrets` table). Restarts and redeploys reuse them, so logins survive updates.
- Want to manage them yourself? Set `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and/or `CRED_ENCRYPTION_KEY` as variables on the `api` service — an environment variable always beats the stored fallback. (`CRED_ENCRYPTION_KEY` must be base64 for exactly 32 bytes: `openssl rand -base64 32`.)
- **Broker credentials** (Webull keys, Tradier token) are entered inside the app after you log in, and are stored encrypted in your database. To enable the options-analytics overlay server-wide you can instead set `TRADIER_API_TOKEN` on the `api` service.

## Updates

Your `api` service is connected to the template's GitHub branch. Redeploying the service (or enabling auto-deploy in the service settings) rebuilds from the latest `main`; database migrations run automatically on every start.

## Troubleshooting

- **`/v1/health` doesn't load** — check the `api` service's deploy logs in Railway; the health check is `/v1/health` and the app logs a full Nest boot when healthy.
- **App can't connect after pasting the URL** — use the exact `https://…railway.app` origin with no trailing path; the in-app **Test connection** button tells you whether the URL is reachable and healthy.
- **Fresh database** — deleting the Postgres volume erases users and stored broker credentials; the API will regenerate secrets and start empty on the next boot.
